WDash documentation

Version 3.1.5. Everything below is behaviour of the shipped code — where a number appears it was measured, and where something is a limitation it is written as one rather than left for you to find.

What it is

WDash is a web front end for telemetry that already lives somewhere else. It reads logs, traces and synthetic checks out of the stores you already run, puts one search screen and one dashboard builder over all of them, and puts authorization in front — because Elasticsearch has no row-level security, Loki has no users, and "who may read the payments service's traces" is a question none of them answer.

Three things follow from that, and they shape everything else on this page.

It never collects

No ingest path, no agent on your application hosts, nothing written into your stores. WDash being down costs you a dashboard, not telemetry.

It is meant to be the only path

Authorization lives in the application, so a cluster that is directly reachable makes it worthless. Put WDash on the network path, not beside one.

A failure never looks like emptiness

A quiet window and a backend that did not answer are different facts, and the screen says which one it is. This is the rule most of the code is organised around.

What it is not

  • Not an ingester. Run an OpenTelemetry Collector and point WDash at the storage behind it.
  • No metrics signal. Logs, traces and synthetic monitors. Metrics have a genuinely different query model, and a screen that rendered Prometheus badly would be worse than not having one.
  • Not a superuser tool. system:admin opens the configuration page and grants no access to logs or traces on its own.
Licence

MIT. The two dependencies that are not permissive — ldap3 and psycopg, both LGPL v3 — are used as libraries over their published interfaces, which is what the LGPL is for, and neither pulls WDash's licence with it. tests/test_dependency_licences.py refuses anything proprietary or source-available.

Install

Two secrets, one process, one page. Nothing about a data source or an identity provider is installed — those are typed into the browser once WDash is up, and take effect the moment they are saved.

1. Get it

The container is the short road. It publishes 5001 rather than the 5000 the process serves on, because macOS answers 5000 with its own AirPlay receiver — measured here as a 403 from Server: AirTunes on a machine where the container was answering 200.

# the image, and an Elasticsearch to point it at
$ git clone https://github.com/warewave/wdash && cd wdash
$ cp .env.example .env
$ docker compose up -d

1b. Or from source

$ python3 -m venv venv && ./venv/bin/pip install -r requirements.txt
$ cp .env.example .env
$ ./venv/bin/python main.py          # development server, 127.0.0.1:5001

For anything but a laptop, run it under gunicorn — the shipped image runs --workers 4.

2. The two keys

Both are refused rather than defaulted, and both are refused for a reason you would otherwise meet later and worse.

$ python -c "import secrets; print(secrets.token_urlsafe(48))"
# → SECRET_KEY

$ python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
# → WDASH_ENCRYPTION_KEY
KeyWhat happens without it
SECRET_KEYSigns session cookies. WDash refuses to start on a published placeholder while SESSION_COOKIE_SECURE is true — the development key, and every placeholder this repository has ever shipped in .env.example or kubernetes/secrets.yaml, is printed in public and would sign the administrator's cookie.
WDASH_ENCRYPTION_KEYSeals every secret at rest: source credentials, the OIDC client secret, the LDAP bind password, and every local account's authenticator. Without it WDash refuses to write a secret as text — so the configuration page cannot save a credential and no local account can finish signing in.
Set the encryption key before anybody signs in

The first administrator's authenticator is sealed with it during enrolment. Rotating or losing the key later means re-entering every stored credential and resetting every authenticator with python -m wdash.store.recover --reset-totp <username>.

3. Where state lives

SQLite for one node and the lab; PostgreSQL for more than one process. The schema is migrated on start-up in either dialect, and the whole test suite runs against both.

DATABASE_URL=sqlite:///data/wdash.db                    # default
DATABASE_URL=postgresql://wdash:···@db.internal/wdash
SQLite means one writer

The Kubernetes manifests ship replicas: 1 and strategy: Recreate for exactly this reason — it is the SQLite file, not caution. Move to Postgres before scaling out; kubernetes/README.md says what to change and in which order.

4. Behind a proxy

Two settings, and one of them is a number rather than a switch.

SESSION_COOKIE_SECURE=true      # HTTPS-only cookie; also turns on HSTS
TRUSTED_PROXY_COUNT=1           # how many proxies are actually in front

TRUSTED_PROXY_COUNT defaults to 0, which ignores X-Forwarded-For entirely and uses the socket address. That header is written by whatever spoke to the proxy, so trusting it without knowing the depth lets a client name its own address and step around the per-address rate limit by changing a header. Set the real number and the address is counted in from the right.

5. The alert evaluator

Only if you want alerts. Run one — two would evaluate the same rules and deliver the same notification twice.

$ python -m wdash.alerts                  # every 30s
$ python -m wdash.alerts --interval 60
$ python -m wdash.alerts --once           # evaluate once and exit, for
                                          # testing a rule without a daemon

6. Open it

http://127.0.0.1:5001. The installation has no accounts, so every route leads to /setup.

On Kubernetes

kubernetes/ installs one WDash: the server, its metadata database on a volume, the alert evaluator beside it, and a plain networking.k8s.io/v1 Ingress.

$ kubectl apply -k kubernetes/
$ kubectl -n wdash rollout status deploy/wdash

Two things have to change before that command, and neither starts without you. The image is not one of them any more: yigitbasalma/wdash-elastic-dashboard:3.1.5 is published for linux/amd64 and linux/arm64, so an apply of these files as they are pulls a tag that exists. For a cluster that pulls from a registry of its own, retag rather than rebuild — a rebuild is a different image under the same version, and which one a node has then depends on when it pulled.

1. The two secrets

Both ship empty, and they are empty for different reasons.

$ kubectl create namespace wdash

$ kubectl -n wdash create secret generic wdash-secrets \
    --from-literal=secret-key="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')" \
    --from-literal=encryption-key="$(python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())')"
KeyWhat an empty one does
secret-keyNothing starts. It used to ship as a working key printed in this repository, so an unedited apply signed every session cookie — the administrator's included — with a string anybody can read. WDash now refuses to start on its development key while SESSION_COOKIE_SECURE is true, so an unfilled Secret fails with a message rather than quietly running forgeable.
encryption-keyThe pod starts and no local account can sign in. There is no guard, because an empty string is valid base64 and nothing can tell it from a key. Every local account needs an authenticator, its shared secret is sealed with this, and the store will not write a secret as text — so enrolment fails, and enrolment is the first thing a new account does. The start-up log says so as an ERROR.
Back the encryption key up with the database

Not separately from it. Changing it later makes every stored credential undecryptable — source passwords, the OIDC client secret, the LDAP bind password — and every enrolled authenticator with them. A sign-in then reports that a stored secret could not be decrypted, and recover --reset-totp is the way out, one account at a time.

secrets.yaml is a template and the kustomization does not apply it: an apply would overwrite what you created here with empty values, and the next restart would refuse to start on a session key it no longer had. Create the Secret once and keep the file as the record of what goes in it.

2. The hostname

The host and tls entries in ingress.yaml. The redirect URI typed on the OpenID Connect card after the first sign-in has to be https://<that host>/auth/callback, and the same URI registered at the provider — a mismatch surfaces as the provider refusing an unknown redirect URI, which names neither.

What is in the pod

ContainerWhat it is
wdashgunicorn, four workers, on port 5000
alertspython -m wdash.alerts, evaluating rules every 30 seconds
nginxthe sidecar on port 8080: static files, and the proxy in front

The evaluator is a separate process in the same pod. Separate because evaluation has to run when nothing is arriving — an agent going completely silent produces no requests at all, and that is when somebody needs telling. Same pod because it reads the same SQLite file on the same ReadWriteOnce volume, and a second pod would have to be scheduled onto the same node to mount it.

Only the sidecar's port is on the Service

The application's own port is not, because TRUSTED_PROXY_COUNT tells WDash to believe X-Forwarded-For: a request arriving directly on 5000 could name any client address it liked and walk through the per-address sign-in throttle with it.

Three questions, and none of them is /health.

A probe agent in the cluster

wdash-agent.yaml is not applied by default, because it needs a token that does not exist until you create the agent.

# Configuration → Agents → Add agent, then:
$ kubectl -n wdash create secret generic wdash-agent \
      --from-literal=agent-token=<the token>
$ kubectl -n wdash apply -f kubernetes/wdash-agent.yaml

An agent inside the cluster measures the service from inside the cluster; one outside measures what your users experience. They answer different questions and it is reasonable to run both — give each its own token, because the agents page identifies an agent by it.

Browser journeys need the browser image, and its memory: Chromium needs gigabytes, not the 256Mi the plain agent is given. The manifest already mounts a writable /tmp, which Chromium cannot start without on a read-only root filesystem.

More than one replica

replicas: 1 and strategy: Recreate are not caution, they are the SQLite file. One ReadWriteOnce volume cannot be mounted by a second pod on another node, and a rolling update tries to start one before the old pod lets go — the symptom is an upgrade stuck in ContainerCreating behind a healthy old pod, which reads as a storage fault.

To scale out, in this order:

  1. Copy the volume into an empty Postgres, from the pod that has the volume — accounts, roles, sources, dashboards, the audit trail, monitors and their history, alerting, all of it: 
    $ kubectl -n wdash exec deploy/wdash -c wdash -- python -m wdash.store.copy \
      --from sqlite:////data/wdash.db \
      --to 'postgresql+psycopg://user:pass@host/wdash'
    It refuses a target that holds anything somebody wrote, counts both sides afterwards, and copies the sealed credentials as they are — so keep the same encryption-key in the Secret.
  2. Point DATABASE_URL at Postgres, check that it starts and that you can sign in, then drop the PVC and its mounts.
  3. Move the alerts container into a Deployment of its own with replicas: 1. Run exactly one, or the same rule pages twice.
  4. strategy: RollingUpdate and as many replicas as you like.

A source saved on the configuration page reaches every replica within five seconds and without a restart: the worker that handled the save is correct immediately, and every other one notices on its next poll.

Network

networkpolicy.yaml says who may reach WDash — the ingress controller, and WDash's own agents. It deliberately says nothing about where WDash may talk: the identity provider, the backends and an alert channel's webhook are all chosen after the policy is applied, and a rule that silently stops an alert being delivered is worse than no rule.

The other half is not in these files

Application-level authorization is worthless if Elasticsearch is reachable around WDash, and that policy belongs in the cluster's own namespace. There is a template at the bottom of networkpolicy.yaml, and the Advisor's SEC001 check exists to keep asking.

kubernetes/README.md carries the same steps beside the files themselves, and goes further on the ones this page summarises.

First run

/setup creates one account. It is a local account, stored in WDash's own database with an Argon2 password hash — not an identity-provider account, and it keeps working when the identity provider does not.

That is the point, and it is also the risk

This account is the way back in after a bad OIDC change, which also makes it a permanent credential to the whole system. Protect it like one, and do not share it.

What happens, in order

  1. You choose a username and password. Minimum twelve characters and no composition rules — length is what actually costs an attacker time.
  2. Setup closes. Checked against the database on every request rather than a flag cached at start-up, so a second worker sees the first worker's administrator immediately. The account is created under a uniqueness constraint: two people submitting the form at the same moment produce one administrator and one clear error, not two owners.
  3. You are not signed in. Setup leaves the same short hold a correct password leaves, and that hold opens the enrolment page and nothing else. It used to sign you in — which with a mandatory second factor would have made the account that matters most the one account that never enrolled.
  4. You enrol an authenticator. A QR code, the same secret in typeable groups, and the whole otpauth:// link — all three, because an authenticator on the same device cannot scan the screen it is on.

The shared secret does not reach the database until a code proves you hold it. An unconfirmed secret on an account is a half-enrolled account that whoever saw the QR may be able to sign in as.

There is no other door

Setup cannot be reopened from the UI. There is no static password and no environment-variable-gated bypass: the old /auth/dev-login has been removed, because a guard that is one environment variable deep is the guard people forget.

Sign in and go to Configuration → Sources → Add source. Nothing is read from the environment, and a source is in use the moment it is saved. Adding a source is the next section, and the lab gives you five backends full of data to point at if you have none to hand.

Adding a source

A source is a connection to somewhere telemetry lives, declared at Configuration → Sources and stored in the metadata database with its own credentials and patterns. One source serves every signal it holds: an Elasticsearch with logs and traces in it is one entry with one credential, not two rows that drift apart at the next rotation.

Test before you save

Add source runs a connection test. A source that holds a credential cannot be saved until that test has passed — a stored credential that has never reached the backend is a configuration that looks finished and answers nothing. A refusal is recorded in the audit trail, including the case where the secret itself could not be read.

A source that holds a credential verifies the certificate

Over https, turning verification off means the source is talking to whatever answered, and WDash would send that credential there on every query. The save is refused, and it is refused whether or not the password is typed again — retyping used to be the way through, which confused consent with protection.

Two remedies, both on the page:

  • Leave verification on. A private authority goes in the trust store of the host WDash runs on, which is where every other client on that host will find it too. There is no per-source CA field.
  • Tick "Forget the stored password". A source with no credential may verify or not as you like.

A plain http source is not what the rule is about — there is no certificate in it to check. A synthetic check has had the same rule since its TLS support was written, and it does carry its own pasted certificate, because the agent that makes its connection runs on somebody else's host.

A password in the address is refused

https://wdash:hunter2@es.internal:9200 is rejected by the URL validator. The URL is stored as typed and shown as typed, so a password written into it would be a credential travelling the address's road — visible on the configuration page and in the audit trail. A bare user@host with no password is allowed. An installation that already stored one is told at upgrade by migration 20, which logs and audits the source masked: it cannot seal the value, because migrations run before the encryption box exists.

Changing one

A source saved in the UI is in use within a few seconds: the worker that handled the save uses it immediately, and the others notice on their next check, at most five seconds later. The stored sources are swapped as a unit and the adapters a running query holds are not closed under it, so an edit never disturbs a query in flight.

A source cannot be renamed while any role's patterns name either the old name or the new one. Renaming primary would turn -primary:secret-* into an exclusion of nothing; renaming a source to staging would hand staging:* everything in it.

The five backends

Elasticsearch

The only one that serves all three signals: logs, traces (its own APM schema and OpenTelemetry's) and synthetic monitors — Heartbeat and the Fleet Synthetics integration write into the same cluster, and a third index pattern is all that separates them from the rest.

It is also the one that answers a whole dashboard in one request, whatever the panel count, because the panels are batched into an _msearch. It reports a real match count, ranks server-side, and can return the raw stored document and the records surrounding one.

Grafana Loki

Logs only, and with fewer capabilities than the name suggests: no field statistics, no context view, no single-record fetch. Loki has neither field mappings nor document ids, and those are declared absent rather than answered with something thinner than the name.

  • A level matches however it was written and wherever it was written: level:WARN finds warn, warning and WARN in Loki's level, severity or detected_level — the same fields, read in the same order, that a record's own level is read from.
  • A negated group such as NOT (a b) is refused with a warning. A chain of line filters cannot say OR, and a query that silently means something else is worse than one that is rejected.
  • A panel counted by a field that is not a Loki label says so rather than drawing an empty chart.
  • It does not report an exact total, so a merged page total including Loki is reported as a lower bound.

VictoriaLogs

Logs only, but with more than Loki: it can count matches and list field values, so a page total is a real count and the field-statistics sidebar is served by the backend. No context view and no raw document — _stream_id names a stream rather than a line, and returning the wrong record is worse than returning none.

Jaeger

Traces only. Two limits worth knowing before you rely on it:

  • It cannot answer "every trace". GET /api/traces without a service is an HTTP 400, so an unfiltered search is fanned across the service list and bounded at twenty services.
  • No per-service volume without a separate metrics backend wired up, so its service list carries names with a span count of zero — rather than a number derived from a sample of fetched traces, which would look like a measurement and be a guess.

Grafana Tempo

Traces only. It returns ids two ways — its search endpoint gives hex, its trace endpoint gives OTLP JSON where ids are protobuf bytes and therefore base64. Both are handled; read as hex, the base64 form produces dangling parents and a flat waterfall that looks like missing instrumentation. A TraceQL query it cannot parse is surfaced rather than swallowed into an empty result. Like Jaeger it reports no per-service volume without a metrics backend.

"Slowest" is the slowest of a sample on Jaeger and Tempo

Neither search endpoint takes a sort parameter — both answer newest-first — so the ranking happens in WDash, over a pool it asks for: five times the page size, between 100 and 500 rows. When that pool comes back full there were more traces behind it, and the list says so in a line of its own. Elasticsearch ranks server-side, so "Slowest" there is the slowest in the window.

OpenTelemetry

WDash's internal model follows OpenTelemetry semantic conventions — a log message is body, its level is severity, service and host live in resource — and adapters translate on read. The lab runs a real collector (./lab.sh up otel) so the OTel path is exercised rather than assumed, which is how it was found that the schemas had been written against a fixture that had itself been written from an assumption.

Capabilities intersect across a merged search

"All sources" can only offer what every source in it can do. Configuring a Loki therefore removes the field-statistics panel from the merged view — it is not hidden as an error, it is genuinely unanswerable. The source breakdown beside it does not come from a capability and stays.

Searching across sources

The Logs screen grows a source picker once more than one is configured, with All sources first. It fans out in parallel and merges by time. There is no default source: a search or a board that names none asks all of them.

The merge is the easy part. What matters is that a backend being down is visible: the page renders from the sources that answered, marks itself incomplete, and names the one that failed — because fewer rows looks exactly like less data.

Three things a merged answer says

  • Which source each record came from. A badge on the row — but only when more than one source is configured. A badge repeated on every row that always says the same thing is noise, and noise is how people stop reading the row footer at all.
  • That a total is a floor. Elasticsearch reports a real match count and Loki does not, so a merged total including one is reported as a lower bound rather than as a number.
  • That it is first-page only. Paging a time-ordered merge needs every source's cursor advanced together, and each backend's cursor means something different. A cursor that silently skips records is worse than no paging, so the merged view stops at the first page — and the pagination line names the merge as the reason rather than blaming the source.

A chart or a terms panel over several sources

Buckets are merged by key, histograms by timestamp. A terms list is trimmed back to the size that was asked for, and when trimming actually dropped something the panel says so — a "top 10" assembled from three partial top-10s is not the top 10, and the panel that does not say so is the one that gets quoted in a postmortem.

To make that less likely each source is asked for more than the page needs — half again plus ten — so the merge has something to trim from rather than something to guess at. Date buckets are never cut: a histogram missing its last hour reads as traffic stopping.

One record lives in one place

Fetching a single record, its context or its raw document takes a ?source=, because those questions have one answer. With one source configured that one answers; with several, a request that names none is refused, as ?source=* is.

Query syntax

The text you type is parsed into a backend-neutral tree and rendered into each backend's own language. Syntax errors are reported with a position, before the query leaves the process, and nothing you type is injected into a backend's query string.

*                            everything
severity:ERROR               field equals value
body:"connection refused"    exact phrase
service:payment*             prefix
duration_ms:[100 TO 500]     range
_exists_:trace_id            field is present
a AND b   a OR b   a b       combination (whitespace means AND)
NOT a     -a                 negation
(a OR b) AND c               grouping
free text                    searched in the message body

Aliases

Elasticsearch and ECS field names are accepted, so people who know that vocabulary keep using it:

You typeIt means

A bare term with no field name is searched in body.

Severity is normalised both ways

The internal vocabulary is OpenTelemetry's — TRACE, DEBUG, INFO, WARN, ERROR, FATAL, and UNSPECIFIED for a level that is missing or unrecognised. Backends write other spellings, and the filter knows them all: WARNING, ERR, CRIT, CRITICAL, SEVERE, PANIC, NOTICE, VERBOSE and FINE each map onto one of the six.

So on a backend that stores what was written, level:ERROR matches error and err, and the sidebar's merged WARN row finds warn and warning alike. A filter for UNSPECIFIED is "none of the known spellings", because nothing writes that word.

What is deliberately missing

Fuzzy matching, boosting and regular expressions are not supported. Unsupported syntax is rejected rather than silently reinterpreted.

Linking into a search

The Logs screen reads query, time_range and start/end from the query string, which is what makes every chart elsewhere a link into it:

/logs?query=level:ERROR AND service:"payment-service"&time_range=24h

The Logs screen

One query box, one window, and four things around the result.

The histogram

Volume over the window, bucketed and split by severity. Click a bar to narrow the window to it. The bucket width is derived from the window, and the alignment matters more than it sounds: a bucket whose interval starts before the window is dropped rather than drawn short, because a first bar a third of a bucket wide reads as a quiet period that never happened.

Field statistics

The sidebar lists a field's most common values with their share of the window, served by the backend where it can be — see capabilities. Click a value to add it to the query.

Saved searches

A query, a window and a source, saved by name. They live in the metadata database beside dashboards — one setting covers both, because leaving the searches on a JSON file when dashboards moved made that migration a half-truth once already. A save or a delete that fails says what the server said; the list does not quietly shorten.

Scope

Which containers you can search is your role's business, not the query's. A role that reaches nothing in a source is told how many containers exist there, not their names — only an administrator is shown the names. A drill-down arriving from a dashboard is answered from that dashboard's source, and the picker on screen moves to match: the control and the records under it used to disagree.

Traces

Three questions, in the order people ask them.

Services by traffic

Span counts and error rates per service over the window. On Jaeger and Tempo the counts are zero unless a metrics backend is wired up — see the backends.

Traces for one service

Slowest, newest, or only the ones that failed. "Errors only" means an error in a service you may see, and a trace whose entry point is hidden from you is still listed — told through its visible services and timed by them — rather than silently dropped.

One trace

A waterfall with self-time, a per-service breakdown, and the log records carrying the same trace id where a log source declares the correlation capability. A trace split across two stores is reassembled into one waterfall, not shown as two halves. A trace that lost spans to a role's exclusion says so, rather than showing a shorter waterfall that looks like missing instrumentation.

A trace panel is checked against traces:read

Not against dashboard:view. A dashboard panel is held to the same permission its screen is; otherwise a shared dashboard is a way around every one of them, which a trace panel was — it filled for a role without traces:read while the trace list beside it on the same board said no.

Building a dashboard

A dashboard is a query, a window, a source and a list of panels. A panel is a question, not a chart: its type says what is being asked, and how it is drawn is the client's business.

The fields on the form

FieldMeans
Name, descriptionWhat the list shows.
QueryThe same syntax the Logs screen takes. Every log panel is filtered by it.
Time rangeThe default window when the board is opened.
RefreshHow often it reloads, and the form says what that costs — see below.

Pinning a board to a source

A board reads every source unless it is pinned. A pin is the source for every signal that source serves: pinned to a cluster that serves logs, traces and monitors, a board reads all three from it; pinned to a Loki, its logs come from the Loki and its traces and monitors from every source, because the Loki serves neither. The board's header says which.

A board pinned to a source that is no longer configured reports that plainly on every panel, instead of falling back to the rest. Quietly answering from a different store is how somebody concludes their data has disappeared. An edit that does not carry the field leaves the stored source alone, for the same reason — on an installation with nothing to choose the field is not even drawn.

What a refresh costs

It depends on the sources it reads, and the forms say so where the source is chosen. Elasticsearch answers a whole board in one request whatever the panel count; Loki and VictoriaLogs are asked once per log panel plus twice for the stat cards.

Measured on the lab

An eight-panel board over 24 hours: 1 request to Elasticsearch, 10 to Loki, 10 to VictoriaLogs — 21 per refresh across all three, and only its own source's share when pinned.

Which sources answered

The four stat cards print how much each log source gave, and every trace and monitor panel names the stores its rows came from. Two stored rows over one cluster are two names under one number, rather than a number that is quietly double.

Size and height

  • Width is 3–12 columns and the grid flows. There is no drag, no row and no position — deliberately not a layout system.
  • Height is 120–900 pixels, and the editor offers four named ones: 180 ("short — a few rows"), 300 (standard), 450 (tall), 600 ("very tall — a long table"). Any integer in range is accepted, so a stored board is not invalidated by that list changing.
  • Bucket and term counts go to 50; record and alert lists stop at 25. Measured on the lab over app-logs-000001 at 24 hours: 381 bytes of JSON per record against 41 per terms bucket, so four records panels at 50 would put 76 kB on the wire for four cards 300 pixels tall.

Which fields you can group by

The editor asks the source what it can group by and offers that. Where nobody has answered yet — a discovery call that failed, a source that does not say — it falls back to severity, service, host and environment, so a deployment with one of everything still recognises the list.

Two refusals are static, and they are static on purpose:

  • The log line itself is refused — body, message, _msg, line, log. An aggregation on an analysed text field either fails or returns tokenised nonsense, one word per bucket.
  • A name that is not a field name is refused: letters, digits, underscore and dot, starting with a letter or underscore, up to 64 characters. Strict because the name is interpolated into a LogQL sum by (…) clause and a LogsQL filter, and because this question has to be answerable offline — a panel is normalised on every read, and a rule that consulted a backend would turn one stale panel into a board that will not open.

Whether this source can answer http_status today is the source's answer, given per panel at fill time, in a note on the card.

Click-through

A bar, a slice or a row is a link into the Logs screen with the field, the value and the window already set. An "unlabelled" bucket becomes NOT field:*, because "the records with no value here" is a real query and an empty string is not.

Thresholds and comparison

The previous period

Every board fetches a baseline window of the same length, immediately before the one on screen, batched into the same request. If that sub-query fails the comparison is null — it is never reported as a real zero, which would render as "−100%, traffic has stopped".

Thresholds

Numbers that colour a card: warning and critical, over a panel's value.

Thresholds are not alerting

They colour the dashboard. There is no notification, no schedule, no silencing and no history behind them. That is alert rules, which are a different subsystem over different data.

A partial answer gets no badge at all

When a backend returns a result that is short of a shard, the board does not print "within thresholds" — that is a claim about numbers, and there are none to make it from. The card says the answer was partial instead. Elasticsearch reports failed shards, the fan-out propagates it, and the threshold evaluation is skipped rather than run on a smaller number.

Who can see which dashboard

You can see a dashboard if you could see its data. A dashboard resolving to no container you may reach is one you could never have used, so hiding it costs nothing and stops the list advertising what exists — a name like payment-fraud-investigation over fraud-* is information whether or not you can read the index.

That rule needs no new concept and cannot drift out of step with the data boundary, because it is the data boundary. What it cannot express is intent, so a dashboard can also be marked private: the author and administrators only, even among colleagues with the same access.

Two exceptions, both deliberate

  • Authors always see their own. Otherwise a dashboard over an index that does not exist yet is invisible to the person who just wrote it, which reads as "it did not save".
  • system:admin sees every dashboard, because editing or deleting somebody else's already requires it.

How it is enforced

On the list page and every dashboard endpoint. Applied to the list alone it would not be a boundary, only a speed bump. An endpoint answers 404 rather than 403 for a dashboard you may not see, so the URL is not a way to find out which ones exist.

The list says how many are hidden rather than leaving a gap — including when that number is all of them, which is the case where an empty page saying "create your first dashboard" would be actively misleading.

Dashboards stored before this existed default to shared, so nothing disappears on upgrade. The boundary rule now applies to them, which is the change.

Roles and three boundaries

A role is a set of permissions and three independent boundaries. A boundary that is not declared grants nothing — access is explicit or absent.

Services is the one exception and the form says so. The granularity differs by signal on purpose: for logs the meaningful unit is the index, for traces it is the service. A role given every trace store but restricted to application services sees no infrastructure spans at all.

Tempo and Jaeger have no index to grant

Each is one trace store matched by its source's name: *, lab-tempo, lab-* or lab-tempo:* open it, and -lab-tempo beside * keeps it closed.

Changed in 3.0

2.4.0 and earlier asked only whether a role had any log container, so a role granted nothing but Elasticsearch trace indices (otel-traces-*) read every trace in Tempo and Jaeger. Such a role now needs the store's name added. The three shipped roles use * and are unaffected.

The group names are namespaced, and that is a security choice rather than a preference: a directory almost certainly already has a group called admins, it usually means domain administrators, and mapping it to system:admin by default would hand WDash's highest privilege to whoever is in it.

Before you save a role

Boundary fields stay free text, and that is a decision. Containers rotate: a role granted app-logs-000001 by name silently loses access the day -000002 appears, which is a worse failure than a typo and a much quieter one. Patterns survive rotation, so patterns stay.

The danger was never typing — it was typing blind. So every field shows what it matches as you type, against the containers this installation actually has, and flags the two outcomes worth flagging:

  • matches nothing — a valid choice, and also exactly what a typo looks like;
  • matches everything — the dangerous direction. * where app-* was meant saves cleanly and grants the whole cluster.

browse… beside each field lists what exists, offering a rotation-proof pattern first and the exact name as the deliberate alternative. The matching runs on the server: reimplementing the pattern language in the browser would give the product two of them under one name, which is a bug this codebase has already had once.

When a role is edited the page reports what the change does — which containers it starts and stops reaching, which permissions it adds and removes, and whether the net effect widens access. An end state is easy to read and impossible to review: app-* and ap-* both look deliberate and both produce a plausible count.

Authorization is resolved per request

The session carries identity only — who you are and which groups the provider asserted. What you may do is read from the metadata store on every request, cached for a few seconds per worker.

Permissions used to be written into the session cookie at sign-in, which meant revoking a role saved successfully and changed nothing until the person happened to sign out: an administrator shown a revocation that did not happen. A role change now reaches every worker within about ten seconds with no coordination between them — a bounded window that can be written down, replacing "until they sign in again", which is unbounded.

A local account's own role is stored with the account and beats every mapping, and it is read per request like everything else. An account that is disabled or deleted stops being able to do anything on its next request, not at its next sign-in.

The pattern language

Four forms, in every boundary, services included:

*            everything
app-*        prefix
*-audit      suffix
*payment*    middle

A bare pattern applies to every source

A role granted app-* reaches app-* in each configured source, so adding a source widens what existing roles reach. Write source-name:pattern to hold a rule to one source.

The default is the wide one

This is stated as a limitation rather than dressed up as a feature. If it is not what you want, qualify the rule or exclude what should stay closed.

A colon qualifies only when a source has that name

Names contain colons — OpenTelemetry's default service name is unknown_service:java — so a colon that names no source is part of the name. unknown_service:java grants that service, and -unknown_service:* hides every one of them. The role preview says when a rule's colon names no source.

A source's name cannot contain a colon, and a source cannot be created or renamed with a name that roles already write before one.

An exclusion beats every inclusion

A pattern prefixed with - is an exclusion, and it wins regardless of the order rules are written in. A role is a set, not a program, and a rule whose meaning depends on typing order is not reviewable in any list that displays it.

app-*  -*-pii-*        the app family, never the sensitive ones —
                       and it keeps meaning that as new indices appear

*      -payments       every service except payments, in every store

-secret-*              grants NOTHING. An exclusion on its own is a
                       role with no access, not a role with all of it

Exclusions can be source-qualified too, with the - on either side: -primary:secret-* and primary:-secret-* are the same rule.

A check made without knowing the source fails closed both ways: a qualified grant does not apply, and a qualified exclusion does.

Permissions

Every permission lives in one catalogue, which is what lets the configuration page offer a checked list rather than a text box. A name the catalogue does not know is refused rather than stored: a permission that grants nothing while looking configured is worse than one that was rejected. logs:raed used to save cleanly, grant nothing and say nothing — on the one page whose entire job is access control.

PermissionGrants
logs:readOpen the Logs screen, search it, read a record with its surrounding lines. Which logs is decided separately, by the role's containers.
traces:readOpen the Traces screen, search it, open a waterfall, and fill a trace panel on a dashboard. Narrowed by the role's trace stores and services.
monitors:readOpen the Monitors screen, and fill a monitor or certificate panel. Not narrowed by containers — a monitor is about an endpoint, not an index, and a role's log patterns say nothing about which endpoints somebody may see.

dashboard:createBuild new dashboards. A dashboard cannot reach past its author's own boundaries.

A retired name is translated, not dropped: logs:search becomes logs:read on the way in, so an upgrade does not quietly narrow somebody's access. Splitting those two produced roles that could not be used — logs:read alone opened a page where every search failed, and logs:search alone worked in the API while the page refused to load.

Nothing can recover from losing system:admin

So four invariants refuse any change that would leave nobody able to administer:

  • editing a role's permissions or its groups,
  • deleting a role,
  • reassigning yourself through the mappings table,
  • demoting, disabling or deleting a local account.

"Would this lock me out?" is answered by the resolver's own rule, groups and all, applied to the picture after the change — not by a second, shorter copy of the rule, which is what it used to be and which refused edits that were harmless while allowing ones that were not.

A role something still points at cannot be deleted: the default role, a role a mapping names, or one a local account holds. Deleting the default role used to succeed, and the page then showed its first role — admin — as the default, so the next save made everybody unmapped an administrator.

A refused attempt is recorded alongside the successful ones. It is the more interesting row.

Who gets which role

One order, applied in one place, and it is a pure function of the stored definitions — so the page can ask it "what would this person be after this edit?" rather than carrying a second copy of the rule.

  1. A local account's own role, stored with the account. This is what makes it the way back in.
  2. A direct mapping by email.
  3. A direct mapping by username.
  4. The first group — groups sorted, roles sorted — that a role lists. Sorted so two groups matching two roles resolve the same way every time, rather than depending on assertion order.
  5. The default role.

Mapped roles are chosen from a list and permissions are checkboxes, for the same reason the catalogue exists: a name that does not exist grants nothing while looking configured.

Directory usernames are case-sensitive; local ones are folded

A directory matches uid case-insensitively, so alice, Alice and ALICE all sign in — and WDash used to keep whatever was typed, making each of those a different person with a different role, different dashboards and a separate thread through the audit trail. Measured against OpenLDAP with alice mapped to admin, typing Alice landed on the default role, silently.

The username is now read from the attribute the user filter looks people up by — uid, sAMAccountName, whatever that filter names — and a directory that returns nothing for it leaves the typed name alone. OpenID Connect never had this: there the username is a claim the provider sends.

On upgrade: somebody signing in as Alice against a directory holding them as alice becomes alice at their next sign-in. That is a different name from the one owning their dashboards, and nothing moves them — merging two names is a decision about people, not about data. A direct mapping written against the old spelling should be rewritten.

If the resolver cannot read the store

It serves the last good picture. If there is none it falls back to a deliberately narrow role — logs:read and dashboard:view, no containers, no trace stores, no services — so a database blip is not an access-control incident. A resolver that failed open would be one.

Local accounts and TOTP

Local accounts live in WDash's own database with Argon2 password hashes. They are managed at Configuration → Authentication → Local accounts: create, set a role, disable, enable, reset a password, reset an authenticator, delete.

Every local account needs a second factor

A password alone is a shared secret that travels: it is typed on other people's machines, reused, and phished. The local account is also the one that keeps working when the identity provider does not, which is precisely what makes it worth stealing.

MomentWhat happens
First sign-inThe enrolment page: a QR code, the same secret in typeable groups, and the whole otpauth:// link. Nothing is stored until a code proves you hold the key.
Every sign-in afterThe code page. One step either side of now is accepted for clock drift; a step already used is refused, because a replayed code is one somebody read over a shoulder or off a screen share.
A correct passwordStarts nothing. It puts the sign-in on a short hold, and that hold opens those two pages and nothing else.
A wrong codeA failure, through the same guard that throttles password guessing — so the lockout, the backoff and the audit trail cover it too.

RFC 6238: SHA-1, six digits, a thirty-second step — what authenticator applications implement. It is about sixty lines in src/wdash/auth/totp.py out of the standard library, checked against the RFC's own published vectors.

Lost phone

An administrator resets it from Authentication → Local accounts, and the person enrols again at their next sign-in. When nobody can open that page:

$ python -m wdash.store.recover --reset-totp alice

Both are audited, and both say what they cost: until that account enrols again, its password alone signs it in.

Directory accounts are untouched

WDash never sees an LDAP or OIDC password and keeps no row for those principals, so a second factor for them belongs at the provider that authenticates them.

LDAP and OpenID Connect

Configured at Configuration → Authentication and nowhere else — nothing about a provider is read from the environment. The client is built per request, so an administrator can repair a broken provider and try again without a restart. A provider switched off is off, even with its settings still filled in.

At most one directory

Either LDAP or OIDC signs people in, never both. Ownership here is the username — a dashboard belongs to created_by, a mapping is written against a name — with no provider attached to it. With two directories open, a principal at one who can choose preferred_username signs in as somebody at the other and gets their dashboards and their role.

Which one is in force: both stored and enabled, the row saved most recently wins and ties go to LDAP, so the answer never depends on row order; one, that one; neither, local accounts only.

Enabling the second is refused on the page, in words that say how to switch — turn the first off and save, then enable the other. That second save is the confirmation, and it says what those names already own: how many dashboards and mappings belong to names that are not local accounts, a few of them by name, and that whoever signs in as one of them through the new directory inherits them. Nothing is migrated and nothing is scoped by provider: a name keeping what it owns is exactly what makes a deliberate switch work.

Switching one on takes a card that can sign somebody in

ProviderRequiredAlso on the card
OpenID ConnectClient ID, Discovery URL, Client secret Redirect URI, Scopes, username / email / groups claims
LDAPServer, Base DN — plus a Bind password wherever a Bind DN names a service account to bind asUser filter, Group attribute, CA certificates

A card missing any of those is refused with the fields named, on the server and in the browser, and nothing is saved. A card that is switched off may be half-filled — that is a draft somebody is coming back to — but what is filled in has to be usable either way: a server address without ldap:// or ldaps://, or a discovery URL that is not http(s) or resolves to a link-local address, is refused whether or not the switch is on.

An empty card with nothing stored behind it is not saved at all; a card that exists may be blanked, which is how a provider is removed.

Before this, an empty card saved, switched on, reported itself as "in force now", and refused the other directory as a second one — while every sign-in through it was declined out of sight, in a log line.

LDAP

  • The bind is as the user, with the password they typed. Finding their entry with the service account proves the account exists, not that the password is right; treating the search as the check is a complete bypass that looks like working code.
  • ldaps:// certificates are checked against the system's CAs, or a CA file named on the page. The bind carries a person's password, so a directory whose certificate is not checked hands that password to anything that answers in its place. Turning the check off is a switch somebody has to choose, and it is logged on every sign-in. A CA file that cannot be read is refused when it is saved. An ldaps:// server may be named by address when its certificate carries that address.
  • ldap:// sends passwords in clear text, and the page says so.
  • An outage is an outage. A directory that cannot answer — unreachable, certificate refused, service account refused, a search that fails — is reported as that and answered with a 503. It is not recorded as a wrong password, so an outage cannot lock anybody out. A local account's name is never asked of the directory, so an outage cannot stop its wrong guesses being counted either. The user's own bind refused for the account — locked by a password policy, inactivated — is a wrong password, not an outage.
  • ldap3 is LGPL v3 and kept behind src/wdash/auth/ldap_auth.py so it can be replaced in one file.

OpenID Connect

  • Scopes default to openid email profile groups — groups because roles are mapped from groups, and a provider that gates that claim behind a scope sends nothing without it. A provider that refuses a scope it does not know needs the list changed on the card.
  • A blank Redirect URI means this WDash's own /auth/callback as the browser reached it, which is right on a laptop. Behind a proxy that terminates TLS, type the https:// address and register the same one at the provider.
  • An email counts only when email_verified is true. Roles can be mapped to an address, and a provider that lets people set their own address would otherwise let them take somebody else's mapping. A provider that never sends the claim has to be trusted explicitly, and email_verified speaks for the email claim only.
  • Choose a username claim your users cannot edit. Ownership and name mappings trust it. A dotted name reaches into an object (realm_access.roles).
  • Without a username, the fallback is the verified email, then sub — unless the provider sent an address it did not verify, as ADFS and Entra v1 tokens do. That sign-in is refused, naming the setting, rather than signing the person in as an opaque id that owns none of their dashboards.
  • Named nowhere, the claims are preferred_username, email and groups.
No directory may sign somebody in under a local account's name

That name owns the break-glass administrator's dashboards. Such a sign-in is refused and audited — checked against the name the directory answers with as well as the one that was typed, because a filter matching more than one attribute makes those two different strings, and the second is the one the session would get.

What is said out loud

  • A directory configured and not in use gets one neutral line on the sign-in page, so somebody whose usual door has gone is not told "Invalid username or password" for a reason that is not theirs.
  • A directory in force whose settings cannot be read — a rotated encryption key, a half-filled row — closes the door rather than handing the installation to the other one.
  • An installation that already has both gets a start-up warning, one two directories configured audit row for the installation (not one per worker, and none on later restarts while nothing has changed), and a banner on the configuration page. Measured with the four worker processes the shipped image runs: four rows before the write lock was taken ahead of the read, one after, on SQLite and on Postgres.
  • A resolution that changes while WDash is running is audited as directory in force changed.
  • Turning off the directory you arrived through is refused when no enabled local account can administer and no other directory would take over.

Agents

WDash probes nothing. An agent runs somewhere a user would be — another region, a branch office, a laptop — pulls its configuration from WDash, runs checks on its own schedule, and pushes results back. WDash never connects to it, so it works behind NAT and needs no inbound port. Restarting WDash misses no check, and two WDash replicas do not double every probe.

$ python -m wdash.agent --server https://wdash.internal --token <token>

# or the image — two of them, and the small one is the default.
# Published for linux/amd64 and linux/arm64.
$ docker pull yigitbasalma/wdash-elastic-dashboard:3.1.5   # server, 79MB
$ docker pull yigitbasalma/wdash-browser:3.1.5            # + Chromium, 557MB

$ docker run -d yigitbasalma/wdash-browser:3.1.5 \
      --server https://wdash.example.com --token <token>

Create the agent at Configuration → Agents; the token is shown once. Prefer WDASH_AGENT_TOKEN over --token, because an argument is visible in ps. Anybody running a probe for http and tcp checks should use the small image — the browser is most of the second one and nothing in the first needs it.

Those are what the registry stores and what you wait for: the sum of the compressed layers, read off the published manifest, for linux/amd64. The arm64 halves are a little larger — 81MB and 592MB — and docker images shows a third number again, disk usage after unpacking, which depends on your storage driver (370MB and 2.39GB here, over containerd's overlayfs snapshotter). Three numbers for one image is not a mess to tidy up; it is three questions. The ratio is the part worth remembering and it holds under all of them: the server is about a seventh of the browser image.

Three failures kept apart

Conflating any two of them produces a monitoring system that lies.

What happenedWhat WDash shows
The target is downA result, status down, with a reason.
WDash is unreachableResults spool to disk and are sent from there. Nothing is reported as down — a check that ran during an outage is the most valuable check there is, and exactly the one that cannot be delivered at the time.
The agent is deadIts monitors go unknown, never down. "Nobody looked" is not "it is broken", and a false outage is how a monitoring system trains people to ignore it.

An agent is treated as gone five minutes after its last word — three intervals of the slowest sensible schedule, long enough that one missed beat is not an alarm and short enough that a dead agent is noticed within minutes.

Numbers worth knowing

LimitValueWhy
Configuration poll60sCheap: the server answers with a content hash and the agent reschedules only when it changes.

# runs EVERY check once, ignoring the schedule, and reports what was accepted

HTTP and TCP checks

Three kinds: http, tcp and browser. ICMP is absent on purpose — it needs a raw socket and so a privileged container, which is a decision rather than a type that quietly appears in a list.

Create them at Configuration → Monitors, assign each to one or more agents, and give each an interval and a timeout. A monitor assigned to no agent reports unknown.

What an HTTP check can carry

  • Method, headers, body, and an expected status.
  • Credentials, sealed with the encryption key.
  • A TLS setting: verify normally, trust this certificate (pasted on the form — the agent runs on another host, so the host trust store argument does not apply here), or do not verify — expiry only.
A TLS setting needs an agent new enough to read it

Both settings are sent to every agent assigned to the check, and an agent older than this release ignores them: it verifies against the public roots, so the check stays down with the OpenSSL message and no sentence about the box that would answer it. Nothing leaks that way — WDash withholds an expiry-only check's headers, cookies and credentials before they reach any agent, whatever its version — but the setting does nothing until the probe is upgraded. The agent's own row reports its version; nothing on the Checks table says so yet.

TLS certificates

Every check that speaks TLS reports the certificate it saw: subject, issuer, fingerprint and expiry. The certificate panel and the Monitors screen group those rows by fingerprint and count the checks — one endpoint watched by an agent and by Heartbeat is one certificate watched twice, not two certificates. That is what a certificate rule alerts on.

Browser journeys

A multi-step check through a real Chromium: sign in, add to basket, check out. It is a step list, not a script — nine verbs, and the agent never evaluates anything you wrote.

VerbTakes
Go toA URL. Must be the first step, and must be http(s).
ClickA selector.
Type intoA selector and text.
Expect elementA selector.
Expect textText.
Expect no textText.
Expect URLWhat it should contain.

A journey must start with go to and must contain at least one expect — a journey that asserts nothing passes whatever happens. Fifty steps maximum; a single step waits at most 60 seconds (10 by default), and the whole journey at most 10 minutes.

Why not a script

  • A step list can be rendered. A journey shows as seven rows with seven durations, which is what makes "it got slower at step 4" a sentence anybody can read. A script is one number.
  • Editing a monitor stops being remote code execution on every probe host. In a tool where twenty people share a configuration page, that is not a theoretical distinction.
  • The failure names the step. step 5 (expect_url): expected /dashboard, got /login says the login silently failed. TimeoutError: waiting for selector says somebody has to go and read the script.

It is a real limit: a journey that needs to compute something cannot be written.

Passwords in a journey

{{ secret.name }} is the only interpolation there is. A journey that signs in needs a password, and a password typed into the steps column is a password in a database column, in a form field and on a screen. Secrets are named on the monitor and sealed with the encryption key.

A journey needs a browser agent

Assign it to one. An agent without a browser reports nothing for it and says so in its own log, so the journey reads unknown — "no agent has reported a result for this check" — rather than down. A probe that cannot look is not evidence that a checkout is broken.

Failure screenshots

The page as the browser saw it when the step failed, kept for seven days (monitoring.screenshot_retention_days). At most 512 kB each; the agent downscales, and this is the backstop for one that does not.

An Elastic screenshot is reassembled, and can arrive incomplete

A monitor.type: browser check from Heartbeat or the Synthetics integration is read down to the individual step — name, outcome, duration, the error on the one that broke, and the page as the browser saw it. That last one is not a stored image: Elastic writes a reference to 64 tiles and the tiles themselves, addressed by content hash and shared across every run of every monitor. WDash fetches the tiles and the browser draws them.

So whatever prunes synthetics-browser.screenshot-* removes tiles that newer screenshots still point at — the screen says how many are gone rather than drawing the gap. And a step that never ran has no screenshot at all, so no button is offered for one.

Alert rules

Three kinds, evaluated by python -m wdash.alerts every thirty seconds. They are about monitoring, not about log volume — see thresholds for the difference.

monitor_downA monitor has been down for threshold consecutive evaluations.threshold 1–100, default 3

Every rule also takes a selector — which monitors or agents it is about — a channel, and repeat minutes (0 means notify once per transition).

A rule reads through the hub

Which is what makes one rule cover Heartbeat and WDash's own agents alike: both are monitor sources, and the rule asks the hub rather than the agent table.

Firing, and not un-firing by accident

An alert transitions between ok and firing, and the transitions are what get delivered. Two rules about that are worth reading before you trust it:

A probe dying mid-outage does not close the incident

Every observation carries whether it is known. A monitor that goes unknown — its agent went silent — is held: the firing alert stays firing, and no "resolved" is sent. Previously the sweep saw "this subject is no longer bad" and resolved it, so the outage ended on screen because the thing watching it died.

The same holds for a certificate whose remaining life cannot be read. That is not "the certificate is fine".

A monitor that stops existing does resolve — with the detail "no longer being checked", which is a different sentence from "recovered" — and the history keeps the label the alert fired under, so the resolution names the same thing the alert did.

Run one evaluator. Two would evaluate the same rules and send the same alert twice; the state table is shared, so the second would usually find the transition already made — and "usually" is not a guarantee worth relying on.

Channels

One kind: webhook. A URL, optional headers, and a POST per transition.

A credential in the URL is stripped from what is displayed

A webhook URL often carries a token — that is how Slack and most incident tools authenticate. WDash stores it, sends it, and never shows it: the channel row displays the host only, and a credential written as user:pass@host is removed from that host rather than printed beside it. Migration 21 repairs channels stored before this.

Headers are sealed with the encryption key like every other secret, so a channel cannot be created while no key is configured.

Delivery is recorded, including when it fails

Every notification writes a history row with the rule, the subject, the transition, the detail, and whether it was delivered. The "alerts nobody received" panel and the Alerts screen both count the undelivered ones, because an alert nobody received reads as nothing being wrong.

Silences and history

Silences

A subject, an expiry and a reason. While a silence is active the state machine keeps running — transitions are evaluated as normal — and nothing is delivered. Silences expire on their own and are pruned; there is no never-ending silence, because the silence nobody remembers is the one that hides the next outage.

History

The Alerts screen lists transitions newest first, filterable to the undelivered ones and to a window. Counting is done by last word: a subject that fired and resolved inside the window is one closed incident, not two rows of noise — counting every evaluation would be about 2,880 rows a day per subject at a thirty-second interval.

Health and probes

Three endpoints for three different questions. Two are for probes; the third is for people and alerts.

EndpointAnswersRead by
/livezDoes this process answer? Asks nothing else.Liveness and startup probes
/readyzDoes the metadata store answer — which decides whether anybody can be served at all.Readiness probe
/healthEvery backend's reachability and the running version.People and alerts. Not probes.
 
$ curl -s localhost:5001/livez
{"status":"alive","version":"3.1.5"}

$ curl -s localhost:5001/readyz
{"status":"ready","store":"connected"}

$ curl -s localhost:5001/health
{"main-elasticsearch": "connected",
 "status": "healthy",
 "store": "connected",
 "version": "3.1.5",
 "wdash-agents": "connected"}

/health asks every backend at once and answers within two seconds; one that has not answered by then is reported unreachable. The report is then reused for ten seconds, so a poller cannot hold a worker per poll on a backend that hangs.

"Every backend" means logs, traces and monitors, each asked once however many signals it serves. The report is one flat object keyed by source name, so:

  • a source whose name collides with a key the report already uses — store, status, version, degraded, detail — is reported under source:<name> instead;
  • two different sources sharing a name get one line between them, because the key is the name;
  • only the metadata store decides the status code. A backend being down is reported, not returned as a 503 — that would take a whole deployment out of a load balancer over an Elasticsearch that is reindexing.

The failure branch used to return the exception's text to an unauthenticated caller, which on a connection error is the backend's address. It names the source and says "unreachable" now.

The audit trail

Who changed what, in the authorization configuration. Append-only, and not deletable from the UI — an audit trail an administrator can edit is not an audit trail.

Logging already said that a change happened. What it could not answer is "what could this role see last Tuesday" — the question that comes up exactly once, after something has gone wrong, by which time the log has rotated and the current state is the only state anybody can see. So each row carries the resulting state, not just the fact of a change.

Refusals are recorded too. A refused attempt to grant somebody administration is the more interesting row.

Forwarding it somewhere else

Two sinks: Splunk HEC and Elasticsearch. Configured at Audit → Forwarding, swept in batches of 500.

The database stays authoritative and doubles as the queue: every row carries a forwarded_at, and forwarding is a sweep over the rows that do not have one yet. That shape buys two things an in-memory queue does not:

  • History is shippable. Point WDash at a Splunk today and the entries from before today go too, because "not forwarded" is a fact stored per row rather than a thing that only existed while the process was up.
  • A restart loses nothing. An in-memory queue drops whatever it held, and the rows it dropped look identical to rows that were delivered.

Delivery is at-least-once, never at-most-once. If a batch is written and the process dies before the rows are marked, the batch goes again. Duplicated audit entries are a nuisance; missing ones are the failure this whole subsystem exists to prevent, so the choice is not close.

The sinks are deliberately small and dependency-free — an HTTP POST each. Retry policy, backpressure and batching strategy belong in the collector on the other end, which every one of these destinations already has.

CSRF

On, over the method rather than a list of routes — so a route written next year is protected before anybody remembers it exists. Every POST, PUT, PATCH and DELETE carries a token tied to the session: a hidden field in a form, X-CSRF-Token for a fetch. Without it the request is refused with a 400 and a page that says what to do.

The one exemption is the agent API, which sends a bearer token and no cookie and therefore has no ambient authority to borrow.

The suite runs with it on — the test client carries the token the way a browser does — so the protection is exercised by four thousand tests rather than by the handful that are about it. The history is worth keeping: Flask-WTF had been installed and never initialised, while five test configurations set WTF_CSRF_ENABLED = False, which reads as "switched off for tests" and therefore as "on in production". It was never on.

Upgrading

Migrations run on start-up in both dialects. Three upgrades need a decision from you rather than a migration.

From JSON files to the database

Dashboards and saved searches are in the metadata database by default. An installation that predates that has a data/dashboards.json, and perhaps a data/saved_searches.json beside it, and has lost nothing — but nothing is reading those files.

$ PYTHONPATH=src python -m wdash.store.migrate_cli --dry-run
$ PYTHONPATH=src python -m wdash.store.migrate_cli

WDash says so at start-up, naming both files and how many records in each the database does not have, and the pages say it too — the dashboards page carries the count instead of "Create your first dashboard", the saved-search list says how many are in the file instead of "No saved searches yet". Both give the path and the command to an administrator only, and both go quiet the moment the migration finishes, without a restart.

With no paths given the tool reads the file the application itself reads, prints both absolute paths, and stops with a non-zero exit if a file it is about to read is not there — rather than reporting "0 moved". Pass --allow-missing-dashboards, --allow-missing-searches or --allow-missing for a deployment that really has none. The JSON files are left untouched, so the move is reversible.

DASHBOARD_STORAGE=file keeps them, unchanged and supported, with one worker: the file store reads the whole document, changes it and writes it back, so two workers editing different dashboards lose one of the edits — silently, because both writes succeed.

Measured, three trials each

4 processes × 8 creates against the JSON file reported 32 successes every trial and left 8, 9 and 11 rows. The same 32 into SQLite reported 32 and left 32, every trial. How much is lost varies with the timing, which is the point.

From a cluster declared in the environment

2.5 and earlier registered an Elasticsearch from ELASTICSEARCH_URL and the seven variables around it, and an OpenID Connect provider from OIDC_CLIENT_ID and the eight around that. Nothing reads them now.

Before upgrading, add that cluster under Configuration → Sources with the same index patterns, and save the provider on the OpenID Connect card. A process that still has any of those variables set says so at start-up as an ERROR naming them and the page — it does not import them, because a one-shot import at start-up is the mechanism that was removed. Local accounts are unaffected either way.

A board or a search that names no source now reads every source

It used to read one — whichever was stored first — and on a mixed installation that is a different number.

Measured on the demo's five stored sources, rolling 24 hours

An unpinned board read 1,115 records from the Loki alone and now reads 15,431 (13,245 from the cluster, 1,066 from the Loki, 1,120 from VictoriaLogs, twenty minutes later). Its trace list for api-gateway was empty, because the oldest trace source was a Tempo with no such service, and lists ten traces from the cluster now. A bare /api/search answered 5 records from the Loki and answers 14,353 across all three, with the breakdown.

The cost moves with it: an unpinned eight-panel board was 10 requests to the Loki per refresh and is 1 to the cluster, 10 to the Loki and 10 to VictoriaLogs.

Pin the boards that should read one source; the rest say on screen which sources answered.

The Cluster Advisor

/advisor inspects a connected Elasticsearch read-only and reports misconfigurations with concrete fixes: shard sizing and density, mapping problems, cache effectiveness, index lifecycle, JVM and disk pressure, security settings. It runs headless too, which makes it usable in CI:

$ PYTHONPATH=src python -m wdash.advisor --url http://localhost:9200
$ PYTHONPATH=src python -m wdash.advisor --url https://es.example:9200 \
      --username wdash --password-file /run/secrets/es \
      --ca-certs /etc/ssl/ca.pem --fail-on critical

Nothing is read from the environment. --password-file takes a path or - for standard input — never an argument, which ps shows. The cluster's certificate is always checked; --insecure turns that off and the credentials then go to whoever answers. With --fail-on it exits 2 when it could not look at everything, and exits 2 in any case when nothing could be evaluated.

Two checks are specific to how WDash queries data: MAP001 flags fields WDash aggregates on that are mapped as analysed text — the cause of dashboard panels that render empty — and QRY001 flags a near-zero shard request cache hit rate, which usually means query time bounds are generated at sub-second precision and every request produces a unique cache key.

Troubleshooting

A new source is configured and every page is empty

Check the window before anything else. Every screen opens on the last 24 hours, and a store whose newest document is older than that is healthy, full, and blank. On the lab, ./lab.sh targets reports what each backend holds over exactly that window; against your own store, widen the time range first.

If the window is right, the next question is the boundary: a role that reaches no container in that source is shown a sentence about its role rather than an empty table, and an administrator is shown the container names. If neither says anything, /health says whether the backend answered at all.

"No local account can sign in"

WDASH_ENCRYPTION_KEY is missing or has changed. The authenticator every local account needs is sealed with it. A key that was rotated makes every enrolled secret unreadable; the way back is python -m wdash.store.recover --reset-totp <username> per account, and re-entering every stored credential.

A role was revoked and the person still has access

Wait ten seconds. Authorization is read from the store per request and cached briefly per worker; the window is bounded and there is no coordination between processes. If it survives that, the person is resolving through a path you did not change — the order is the local account's own role, then email, then username, then groups, then the default, and the local account's own role beats every mapping.

Nobody can administer

$ python -m wdash.store.recover --status

That answers whether it is true before you change anything. Then --grant-admin, --enable, or — if the cause is two directories where the losing one held the administrators — --use-directory. See Locked out.

A monitor reads unknown rather than up or down

Nobody looked. Either no agent is assigned to it, or the agent assigned has not reported for five minutes, or it is a journey assigned to an agent with no browser. All three are deliberate: a probe that cannot look is not evidence about the target. The agent's own row on the Agents page says when it was last heard from, and its version.

A TLS setting on a check seems to do nothing

The agent is older than the release that added it. "Trust this certificate" and "do not verify — expiry only" are sent to every assigned agent, and an older one ignores them and verifies against the public roots — so the check stays down with the OpenSSL message. The agent's row reports its version; nothing on the Checks table says so yet.

A dashboard panel is empty while the rest of the board works

Three different causes, and the card says which:

  • A permission. A trace or monitor panel is checked against traces:read or monitors:read, not against dashboard:view.
  • A field this source cannot group by — a Loki asked to count by something that is not a label, for instance.
  • A field mapped as analysed text. The Advisor's MAP001 names them; that is the classic cause of a panel that renders empty against Elasticsearch.

A merged search will not page

It is first-page only, by design, and the pagination line names the merge rather than the source. Pick one source in the picker to page through it.

"Slowest" looks wrong on Jaeger or Tempo

It is the slowest of a sample — neither search endpoint sorts. The list says so in a line of its own when the sample came back full, which means there were more traces behind it. Narrow the window or the service.

A dashboard shows no "within thresholds" badge

The answer was partial — a shard did not report. That is deliberate: a threshold verdict is a claim about numbers, and a short answer has none to make it from. The card says the answer was partial instead.

An alert resolved and the outage had not ended

It should not, and the 3.0 evaluator holds rather than resolves when the monitor goes unknown. If you see it on an older version, that is the bug: the sweep read "this subject is no longer bad" from an observation that was only unknown. Upgrade the evaluator, which is the same image as the server.
