1. Install

Python 3.11 or newer if you run it directly; otherwise the image. Two secrets have to exist before the first sign-in.

$ git clone https://github.com/warewave/wdash && cd wdash
$ cp .env.example .env

# SECRET_KEY signs the session cookie. Any long random value.
$ python -c "import secrets; print(secrets.token_urlsafe(48))"

# WDASH_ENCRYPTION_KEY seals every stored credential AND every
# authenticator secret. Without it NO LOCAL ACCOUNT CAN SIGN IN.
$ python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

$ docker compose up -d
$ open http://localhost:5001
Keep the encryption key. It seals source passwords, LDAP and OIDC secrets, agent tokens, journey secrets and every local account's authenticator. Change it and those values cannot be read back — WDash says so on the page rather than quietly reconnecting without them. Back it up where you back up the database.

Without Docker

$ python -m venv venv && ./venv/bin/pip install -r requirements.txt
$ set -a && source .env && set +a
$ ./venv/bin/gunicorn --bind 0.0.0.0:5000 --workers 4 main:app

The metadata store defaults to SQLite at data/wdash.db. Point DATABASE_URL at PostgreSQL for more than one worker across more than one host; both dialects are exercised by the same test suite on every change.

Kubernetes

kubernetes/ holds the manifests: a Deployment for the server, one for the alert runner, a Service, and a ConfigMap. Liveness and startup read /livez, readiness reads /readyz; /health is the detailed report, for alerts and people rather than for probes.

2. First run

Until somebody claims the installation, every page leads to /setup. Serving screens whose authorization has no owner is not useful.

  • Choose a username and a password of at least twelve characters. Length is the only rule: composition rules push people towards Passw0rd! and add nothing an attacker notices.
  • Enrol an authenticator. Setup does not sign you in — it hands you a QR code, and the code you type back is what starts the session. A password alone signs nobody in.
  • That account is the break-glass administrator. It lives in WDash's own database, so an identity-provider outage is not a lockout. WDash refuses any change that would leave nobody able to administer — including deleting the last local account, and including the one you are signed in as.
Lost the phone? python -m wdash.store.recover --reset-totp <username> on the host. The same tool re-enables a disabled account and switches the directory off.

3. Add a source

Configuration → Sources. A source is a URL, optional credentials, and the signals it serves. It is in use the moment it is saved — the worker that handled the save uses it immediately, the others within five seconds.

BackendServesWorth knowing
Elasticsearchlogs, traces, monitorsOne entry, one credential, whichever signals you tick. Reads OpenTelemetry and Elastic APM trace schemas, and what Heartbeat writes.
Grafana LokilogsNo field statistics, no context view, no single-record fetch — Loki has neither field mappings nor document ids.
VictoriaLogslogsCounts matches and lists field values, so a page total is a real count.
JaegertracesCannot answer "every trace", and reports no span counts without a metrics backend.
Grafana TempotracesSame: no per-service volume without metrics. TraceQL it cannot parse is surfaced, not swallowed.

Two rules the form enforces

  • A password goes in the password box, never in the URL. The address is stored as it was typed and shown on the page; a password there would be on disk in clear text and on your screen. The form refuses it and names the two boxes to use.
  • A source that holds a credential must verify the certificate. Over https, saving with a password and certificate checks off is refused — including when the password is typed again. Install a private authority in the trust store of the host WDash runs on, or clear the credential.

Test connection before you save. Testing a saved source without retyping its password sends that password only where it was saved for: change the address and the test is refused until you type it again.

4. Roles and who signs in

Configuration → Roles & access. A role is a set of permissions and three boundaries.

BoundaryGrants
Log containersIndex patterns, Loki streams, VictoriaLogs streams. app-*, or primary:app-* to mean one source, or -secret-* to exclude.
Trace storesWhich trace indices or which trace source. Separate, because trace data is not log data.
ServicesWhich services' traces. A team may reach a store and still see only its own services in it.
A bare pattern applies to every source. A role granted app-* reaches app-* in each configured source, so adding a source widens what existing roles can see. Write source:pattern when you mean one.

Permissions

logs:read, traces:read, monitors:read, dashboard:view and the create/edit/delete pair, and system:admin. Every dashboard panel is checked against the permission for the data it holds, so a shared board is not a way around any of them — a panel is refused with a sentence and the rest of the board still works.

system:admin is not a superuser. It grants no access to logs or traces on its own.

Who signs in

  • Local accounts, each with an authenticator. Created and managed on Authentication → Local accounts.
  • LDAP or OpenID Connect — one at a time. The page refuses the second and says how to switch, and the switch says what the names it hands over already own. The directory names the person, not the keyboard: a filter that matches uid loosely would otherwise make alice, Alice and ALICE three different people here.
  • Groups map to roles; a direct mapping by username or address overrides the group. Everything is resolved from the database on every request, so a revocation takes effect in seconds rather than at the next sign-out.

5. Dashboards

A board is a query, a set of index patterns, and a panel list you choose: volume over time (optionally split by a field), top values of a field, a single number, a record table, services from the trace store, a trace list, monitors, certificates and alerts.

  • Every log panel on a board is answered in one backend round trip, however many there are.
  • Every count is compared against the preceding window of the same length. If that sub-query fails the comparison is absent — never reported as a real zero, which would render as "traffic has stopped".
  • Every chart and stat card opens the records behind it, inside the board's own patterns and source.
  • Optional thresholds say whether the board is outside what its owner calls normal. No thresholds means no badge — and so does an answer that came back short, because "within thresholds" is a claim about numbers.
  • A dashboard link carries its time range and filter, so what you share is the view rather than the page.

6. Checks of your own

WDash reads what Heartbeat writes, and runs its own. An agent pulls its configuration and pushes results back, so it needs no inbound port.

# on the box you want to check from
$ docker run -d --name wdash-agent \
    -e WDASH_URL=https://wdash.example \
    -e WDASH_AGENT_TOKEN=<the token the page printed once> \
    warewave/wdash-elastic-dashboard:3.0.0 python -m wdash.agent
  • HTTP checks with an interval, a timeout, expected status, and optional headers or basic auth. Each records its response time and the TLS certificate it saw.
  • A private certificate may be pasted and trusted for that check's own origin — or the check can say "expiry only", which verifies nothing and therefore sends no headers, no cookies and no credentials. The page says which, and never guesses.
  • Browser journeys through real Chromium: a step list rather than a script, each step timed, a failure naming the step and keeping a screenshot. Passwords are encrypted and referred to as {{ secret.name }}, never typed into a step. The browser ships in its own image.
  • A silent agent leaves its monitors unknown, not down. A probe that stopped looking is not a site that stopped answering.

7. Alerts

Three rule kinds, because they are three facts with three audiences: monitor_down, agent_silent and certificate_expiring. Each has a threshold ("this many times in a row") and an optional repeat interval.

$ python -m wdash.alerts          # its own process
  • It runs separately because an agent going completely silent produces no requests at all — and that is exactly when somebody needs telling.
  • A recovery is always sent, silence or not. Somebody silenced the noise of a thing being broken; leaving them believing it still is, is not what they asked for.
  • A subject with no reading holds. If the monitor goes unknown mid-incident, nothing is sent and the failure count is kept — the alert does not close and then re-open when the probe comes back.
  • The history records what was not delivered as well as what was, and a delivery that failed is retried rather than lost.
  • A webhook URL is a credential — for Slack and Teams the path is the credential — so it is sealed at rest and never shown. The page shows the host it goes to and nothing that can authenticate.

8. Operating it

EndpointAnswers
/livezWhether the process answers; asks nothing else. Liveness and startup.
/readyzWhether the metadata store answers, which decides whether anybody can be served. Readiness.
/healthEvery backend's reachability and the running version, asked all at once and answered within two seconds. For alerts and people, not probes.

Retention

Check results are kept thirty days, journey screenshots a week, both on settings you can change. The results clock is a ceiling on the screenshot one — a screenshot whose result row has been pruned is an image no screen can reach. Pruning runs from the ingest path, at most once an hour across the installation.

The audit trail

Every configuration change with who made it, and every refused one too. Append-only, exported from the same screen, and optionally forwarded to a webhook. Secrets never appear in it: a URL carrying a password is masked before the row is written.

Upgrading

The schema migrates itself at start-up, under a lock every worker takes, so four of them coming up together is one migration. Read CHANGELOG.md first — its Needs action section is at the top because that is the part you are reading it for.

9. A lab to try it against

The repository ships one. Each backend starts and seeds on its own, so you can bring up only what you want to look at.

$ cd lab
$ ./lab.sh up loki          # or: elasticsearch, victorialogs,
                            #     jaeger, tempo, identity, otel, …
$ ./lab.sh seed loki        # 24 hours of data to search
$ ./lab.sh targets          # what each one holds, and the URL
                            # to type into WDash

./lab.sh up with no target starts the cluster. Seeding is what makes the lab-backed tests meaningful: they ask about the last 24 hours and skip with the command in the message when there is nothing there, because a run full of skips is a run that measured nothing.
