3.1.6 · logs, traces, uptime

Your cluster has no row-level security. Put one in front of it.

WDash is a small observability front-end for logs, traces and synthetic monitoring. Every query it issues carries an explicit authorization scope — log containers, trace stores and services, three boundaries per role, resolved on every request. It is designed to be the only path to the store behind it.

Install Read the docs

One front end, four things behind it

None of the backends is required. Declare the ones you have on the configuration page, and only those.

Logs

Elasticsearch, Grafana Loki, VictoriaLogs. Lucene-style search, a volume histogram split by severity, cursor paging, field statistics, and the records either side of one you are reading.

Traces

Elasticsearch APM, Jaeger, Grafana Tempo. A waterfall with self-time, a per-service breakdown, and the log records carrying the same trace id. A trace split across two stores is reassembled, not shown as two halves.

Uptime

What Elastic Heartbeat writes, and WDash's own agents: HTTP checks and multi-step browser journeys through real Chromium, with the TLS certificate each check saw.

Alerts

Rules over monitors, agents and expiring certificates, sent to a webhook, with silences and a history that records what was not delivered as well as what was.

  • Roles are three boundaries, not one. Log containers, trace stores and services are granted separately, because "can read app-*" and "can read the payments service's traces" are different sentences. Resolved from the database on every request, so revoking a grant takes effect without anyone signing out. How a role is written →
  • One source serves every signal it holds. An Elasticsearch cluster with logs and traces is one entry with one credential — not two rows that drift apart at the next rotation. Adding a source →
  • Search one source or all of them. A merged page says which source answered each record, and says so when a backend is down rather than quietly returning less. What a merged answer says →
  • Everything is configured in the browser. Sources, identity providers and roles, with a connection test before a source is saved and a "what would this reach?" preview before a role is. Everything the process reads →

A failure must never look like emptiness

This is the rule the codebase is organised around, and most of the work is in the difference between two things that look identical on a screen.

"Nothing matched" and "nobody looked"

A quiet window and a backend that did not answer are different facts. A panel that cannot be filled says why, in its own card, and the rest of the board still works.

A silent probe is not a healthy site

An agent that stops reporting leaves its checks unknown, never up and never down — and a firing alert HOLDS rather than resolving, so a probe dying mid-outage does not close the incident.

A number says what it measured

A merged total that cannot be counted exactly is reported as a floor. A board whose answer came back short of a shard gets no "within thresholds" badge at all: that is a claim about numbers, and there are none to make it from.

A boundary says it is a boundary

A role that reaches no trace store sees a sentence about its role, not an empty table. Refusals are named, and recorded in an append-only audit trail along with the changes that were accepted.

What an operator actually holds

PieceWhat it is
The serverOne Python process behind gunicorn, or the image that carries it. The web UI, the API and the configuration pages are all of it.
StateSQLite or PostgreSQL. Accounts, roles, sources, dashboards, monitors, alerts and the audit trail — in a schema you can read.
The alert runnerIts own process (python -m wdash.alerts), because an agent going completely silent produces no requests at all — and that is exactly when somebody needs telling.
AgentsOptional. One per location you want to check from; they pull their configuration and push results back. Browser journeys use a second, larger image so nobody pulls Chromium to run uptime checks.
Your storesUntouched. WDash reads them; it writes nothing into them and collects no telemetry of its own.

Fifteen minutes, honestly

Two keys, one file, one command. The rest is done on the page.

# 1. the two secrets. Without the encryption key no local account can sign in.
$ cp .env.example .env
$ python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
#    that value goes in WDASH_ENCRYPTION_KEY; put anything long in SECRET_KEY

# 2. start it
$ docker compose up -d
$ open http://localhost:5001

# 3. first-run setup creates the break-glass administrator and enrols
#    an authenticator. Then add a source on Configuration → Sources.

Port 5001 rather than 5000, because macOS answers 5000 with its own AirPlay receiver. Nothing on your cluster changes: WDash needs a URL and, if it is protected, a read credential.

What it isn't

3.1.6 is deliberately narrow. If you need something below, WDash is the wrong tool today.

Not in this release

  • Not an ingester. WDash reads stores somebody else writes. Run an OpenTelemetry Collector and point WDash at the storage behind it.
  • A merged search is first-page only. Paging a time-ordered merge needs every source's cursor advanced together, and each backend's cursor means something different — a cursor that silently skips records is worse than no paging. details
  • A bare container pattern applies to every source. A role granted app-* reaches app-* in each configured source, so adding a source widens what existing roles can see. source:pattern avoids it; the default is the wide one. details
  • Loki and VictoriaLogs serve logs only, and with fewer capabilities — no field statistics on Loki, no context view or single-record fetch on either. Declared absent rather than answered with something thinner than the name. the capability table
  • Jaeger cannot answer "every trace", and reports no per-service volume without a separate metrics backend. Its service list carries names without span counts — zero rather than a number derived from a sample. details
  • One directory at a time. LDAP or OpenID Connect, never both; the configuration page refuses the second and says how to switch. details

Every refusal WDash makes, and why, is one table: What WDash refuses.

It is also new. Every backend is exercised against a real one — Elasticsearch, Loki, VictoriaLogs, Jaeger, Tempo, OpenLDAP and Dex in a lab that ships with the repository — on both SQLite and PostgreSQL. But 3.1.6 means "we think this is right", not "this has run in twenty companies for three years".
